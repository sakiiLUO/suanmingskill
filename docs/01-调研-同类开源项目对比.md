# 调研：同类开源项目对比与选型

> 调研时间：2026-10。原则：**优先借鉴经过验证的设计，不直接复制不兼容或来源不明的代码。**
> 表中 star 数为近似值；许可证以仓库 LICENSE 原文为准，版本锁定见 `NOTICE.md`。

## B. 五个重点项目的对比

### 1. lunar-python（MIT）— 本项目采用

- **实现思路**：纯 Python、零第三方依赖。农历用压缩年表，节气与干支用算法推算，在此之上提供 `EightChar`（四柱、藏干、十神、纳音、地势、空亡、胎元命宫身宫）、`Yun`（起运、大运、流年）。
- **依赖**：无。`pip install lunar-python` 即可（sdist，需能编译？实际为纯 Python，直接构建安装）。
- **已知坑**：
  - 不封装真太阳时（作者明确答复过“没有封装”），必须自己做经度差 + 均时差 → 本项目补在 `scripts/solartime.py`。
  - 23:00 后 `getEightChar()` 的日柱仍按当天，不自动换日 → 本项目补 `--late-zi` 两种口径。
  - 节气只提供交节时刻，不提示“你离交界多近” → 本项目补边界告警。
  - 不校验出生地时区/夏令时 → 本项目补 1986–1991 夏时制表与 `--dst` 开关。
- **判断**：计算层直接采用，规则层自研。这是“借鉴经过验证的设计，也只复用许可明确的部分”。

### 2. sxtwl / sxtwl_cpp（BSD-3-Clause）— 不打包，留作交叉校验

- **实现思路**：寿星天文历的 C++ 实现 + SWIG 绑定，VSOP87/ELP2000 系列，`getJieQiJD` 可给到分钟级节气时刻，覆盖公元前 722 年起。
- **坑**：PyPI 无 cp312 wheel（本项目实测 `pip install sxtwl` 在当前 Python 3.12 上**构建失败**）；mac arm64 无 wheel；sdist 安装脚本会从上级 `src` 拷贝（历史 issue）；立春前年柱/四柱反查有未修 issue；同样不含真太阳时；仓库更新变慢。
- **判断**：BSD-3 许可干净，但安装不可靠、停更风险高。**不放进 vendor**，在文档里作为“可选交叉校验”。

### 3. iztro（MIT）— 紫微 v2 候选

- **实现思路**：纯查表 + 规则引擎（安命宫→五行局→十四主星→辅星→大限流年→四化飞星），依赖 `lunar-lite`/`lunar-typescript`/`dayjs`/`i18next`。
- **坑**：JS 生态，Python skill 需要 Node 子进程；不含真太阳时与夏令时；闰月与晚子时只有一种默认口径。
- **判断**：许可允许，架构成熟。v1 不做紫微（范围控制），v2 用 `node` 子进程封装，不移植。

### 4. ziwei-doushu（代码 MIT / 语料 CC BY-NC-SA）— 只取“坑清单”

- **最大价值**：README 记录的历法坑，直接照搬成本项目 `SKILL.md` 的“常见坑”与 `references/01`：真太阳时（经度 + 均时差）、中国 1986–1991 夏令时、闰月四种口径、晚子时换日、时辰序号 0–11 ≠ 钟点、数据集假日期。
- **禁止**：`docs/tianji-ziwei/` 下的倪师讲授内容为 CC BY-NC-SA 4.0（禁商用、具传染性），断语库未开源 → **整目录隔离，不入库**。

### 5. china-testing/bazi（无 LICENSE）— 只借鉴写法

- **可借鉴**：把四柱、冲刑合会、五行计数、大运流年组织成表格化输出的做法；断语与规则的组织层级。
- **禁止**：仓库无 LICENSE = 保留全部权利，代码、断语文本、数据一律不复制。断语还可能源自受版权保护的现代整理本。

## C. 选型结论

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 计算层 | lunar-python（MIT，vendored） | 纯 Python、零依赖、离线、许可干净、覆盖四柱/十神/大运 |
| 规则层 | 自研（solartime.py + 边界告警 + 口径开关） | 这些正是上游缺的部分，也是出错最多的地方 |
| 解读层 | 自研 references | 不引用他人断语库，避免版权与污名化话术 |
| 可选底座 | sxtwl（BSD-3） | 只在能装的平台上做交叉校验，不打包 |
| v2 紫微 | iztro（MIT） | Node 子进程，不移植、不内嵌 |

**为什么不引入更多依赖**：skill 的运行时越简单越可靠；GPL/AGPL、来源不明、无许可证的代码一律不进依赖树。

## D. 许可证合规动作（发布前）

1. 保留 `NOTICE.md` 与 `vendor/lunar_python-1.4.8.dist-info/LICENSE`（MIT 原文）。
2. 依赖树审计：`pip install pip-licenses && pip-licenses --format=markdown`（本项目仅 lunar-python）。
3. 版本锁定：`requirements.txt` 写 `lunar-python==1.4.8`，避免上游许可变更。
4. 若引入 CC BY 4.0 数据：署名 + 链接；CC BY-NC-SA：**禁止**进入商用发行物。
5. 断语全部自写；古籍原文可用，现代点校本/译注/课程内容不用。
6. 建议本项目以 MIT 发布；若你打算闭源分发，lunar-python 的 MIT 允许，但必须保留版权声明。
